# Plan 0008 DSEE

## Approach
`src/device/dsee.rs`, a tiny `Feature` with state `Option<Dsee {on: bool, available: bool}>`. Read `E2 01` first, then `E6 01` (the order the reference uses). The capture already answered "present or not": 0xE2 is advertised, so no stop-and-report step is needed.
Guard: add two exact SET rows (`E8 01 00`, `E8 01 01`); nothing pattern-based, so this task needs no validator hook and can land before the other SET features if convenient.

## Steps
1. Parsers/encoder + tests from the fixture replies.
2. Guard rows and the full `E8` test set (loop over all `(second, third)` pairs, named listening-mode cases, table 2, ReadOnly mode), and update the existing "no E8 row" test to "only the two DSEE rows".
3. Registration (gated on 0xE2), NTFY `E9 01` / `E5 01`, CLI, owner checklist (batch 2).

## Files likely touched
`src/device/dsee.rs`, `src/device/mod.rs`, `src/mdr/guard.rs` (rows + tests), `src/main.rs`, `docs/plan/README.md` cross-cutting rule if the wording needs a touch-up.

## Tradeoffs
Cheap to implement; the only real risk is `E8` reaching the listening modes. Exact payload rows make that structurally impossible (no prefix matching on `E8`), and the exhaustive loop test pins it. Not sharing code with listening modes (same `E6/E8` family) on purpose.
