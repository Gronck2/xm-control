# 0008 DSEE (upscaling)

## Goal
Read and set DSEE (OFF / AUTO).

## Why
Owner's MVP list. Small feature. The owner decided DSEE stays in the MVP only if the headset advertises it; the capture shows T1 function 0xE2 UPSCALING_AUTO_OFF **is advertised**, so DSEE stays.

## Scope
- Gate on T1 function 0xE2. GET `E6 01` -> `E7 01 <OFF 0x00|AUTO 0x01>`; status `E2 01` -> `E3 01 <EnableDisable>` (ENABLE 0x00 = available); SET `E8 01 <value>`; NTFY param `E9 01 <value>`, NTFY status `E5 01 <status>` (reference).
- Fixture decode: `E7 01 01` = AUTO (on), `E3 01 00` = available.
- If status says disabled (`E3 01 01`), show unavailable and do not send SET.
- Dev CLI `--get dsee`, `--set dsee off|auto`.
- **Guard rule (precise).** `E8` is also the listening-mode SET (BGM, upmix, voice contents, sound-leak reduction), which is forbidden in the MVP because of the XM6 reboot hazard. The guard is an exact-payload allowlist, so:
  - allowed, in normal mode only: exactly `E8 01 00` and `E8 01 01` (T1, three bytes);
  - allowed GETs: exactly `E6 01` and `E2 01` (already present for `--probe`); `E0 01` is not needed and not added;
  - everything else starting with `E8` stays unlisted and is rejected (`NotAllowed`): any other second byte (`E8 00`, `E8 02`, `E8 03`, `E8 04`, `E8 06`, `E8 07`, `E8 09`, `E8 0A`, ...), any other third byte (`E8 01 02`, `E8 01 FF`), a short payload (`E8`, `E8 01`), a long payload (`E8 01 00 00`), and `E8 ...` in Table 2;
  - `E2 <other>` and `E6 <other>` (listening-mode status/param reads, connection mode `E6 00|02|05`) stay unlisted too;
  - no blanket `E8` denylist entry (the denylist wins over the allowlist, so it would block the two DSEE rows); the two rows are the only `E8` entries anywhere in the allowlist.
  - The existing guard test that says "no allowlist row starts with 0xE8" is changed to "the only allowlist rows starting with 0xE8 are `E8 01 00` and `E8 01 01`".

## Out of scope
"DSEE Extreme" as a separate value (the protocol only has OFF/AUTO), listening modes (BGM, upmix, sound-leak), connection-quality mode `E6 00|02|05`, the capability read `E0 01`.

## XM6 status
**Confirmed advertised** (0xE2, priority 29) and readable (`E7 01 01`, `E3 01 00`) on firmware 3.1.5. The SET value encoding (`E8 01 00|01`) and the NTFY ids are reference-derived.

## Hardware
**Sends SET commands** (`E8 01 xx`). The PR merges only after the owner confirms the behaviour on the headphones (hardware batch 2).

## Acceptance
(a) Unit tests, with reply bytes from `tests/fixtures/xm6-probe.txt` (`E7 01 01`, `E3 01 00`): parse both values; an unknown value (`E7 01 02`) is an error; SET bytes; not advertised gives None and no traffic; unavailable status blocks SET; NTFY updates state.
Guard tests (table-driven, in `src/mdr/guard.rs`):
- `E8 01 00` and `E8 01 01` accepted in `Mode::Normal`; rejected in `Mode::ReadOnly` (`ReadOnly` error, not `Denied`);
- a loop over every `(second, third)` byte pair of a three-byte `E8` payload in T1, except `(01, 00)` and `(01, 01)`, is rejected;
- explicit named cases rejected: `E8 03 00`, `E8 03 01`, `E8 09 00`, `E8 04 00`, `E8 06 00`, `E8 07 00`, `E8 01 02`, `E8`, `E8 01`, `E8 01 00 00`, and `E8 01 00` in Table 2;
- `E2 03`, `E2 04`, `E6 03`, `E6 00`, `E6 05` rejected;
- the allowlist contains no `E8` row other than the two above.
(b) Owner: toggle OFF then AUTO and report what the headphones say/do; DSEE is hard to hear, so confirm the setting reads back (`--get dsee`) and shows in the phone app/headset. Restore AUTO afterwards.

## Open owner decisions
None (DSEE is advertised, so it stays).
